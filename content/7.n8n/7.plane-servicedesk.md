# Интеграция PLANE → Сервис деск

*Обновлено: 30 октября 2026*

Workflow автоматически забирает из локального PLANE задачи с лейблом `needs-human` и создаёт по ним тикеты в сервис деске. Запускается каждые 5 минут.

## Что делает workflow

1. **Каждые 5 минут** — срабатывает по расписанию
2. **Читает окно** — берёт timestamp последнего запуска из статических данных workflow
3. **Запрашивает PLANE API** — `GET /api/v2/workspaces/{slug}/work-items/?label_id=<needs-human>&updated_at__gte=<last_run>`
4. **Фильтрует** — пропускает задачи, уже переданные в сервис деск (поле `external_source == 'servicedesk'`)
5. **Создаёт тикеты** — POST в сервис деск с полным набором полей (заголовок, описание, приоритет, лейблы, ссылка на PLANE)
6. **Записывает обратную ссылку** — PATCH в PLANE: `external_id = <id тикета в SD>`, `external_source = 'servicedesk'` (дедупликация при следующих запусках)

## Как загрузить

1. Скачайте файл **plane-servicedesk-polling.json** (прикреплён к инструкции)
2. Откройте n8n → «Create workflow»
3. В меню `...` (правый верхний угол) выберите «Import from File» → укажите скачанный файл
4. Настройте переменные окружения (см. ниже)
5. Сохраните и активируйте workflow (кнопка **Publish**)

## Переменные окружения

Установите в n8n через **Settings → Variables** (или в `.env` хоста):

| Переменная | Описание | Пример |
|---|---|---|
| `PLANE_URL` | Базовый URL локального PLANE | `http://plane.internal` |
| `PLANE_WORKSPACE_SLUG` | Slug воркспейса в PLANE | `my-team` |
| `PLANE_TOKEN` | Personal Access Token из PLANE | `plane_api_...` |
| `NEEDS_HUMAN_LABEL_ID` | UUID лейбла `needs-human` в PLANE | `550e8400-e29b-...` |
| `SERVICE_DESK_URL` | Базовый URL сервис деска | `https://sd.example.com` |
| `SERVICE_DESK_TOKEN` | Bearer-токен сервис деска | `eyJ...` |

> **Безопасность:** токены лучше передавать через n8n Credentials (HTTP Header Auth), а не через переменные окружения. После импорта workflow замените выражение `$env.PLANE_TOKEN` на ссылку на credential.

## Первоначальная настройка в PLANE

### 1. Создать лейбл `needs-human`

В PLANE: **Settings → Labels → Add Label**

- Name: `needs-human`
- Color: #FF6B6B (красный — привлекает внимание)

Получить UUID лейбла для переменной `NEEDS_HUMAN_LABEL_ID`:

```
GET {PLANE_URL}/api/v2/workspaces/{slug}/projects/{project_id}/labels/
X-Api-Key: {PLANE_TOKEN}
```

### 2. Назначить лейбл на инцидент

Когда задача требует участия человека — добавить лейбл `needs-human`. Это можно делать:
- Вручную в интерфейсе PLANE
- Через AI-агента или другой workflow
- Через API: `PATCH /api/v2/workspaces/{slug}/projects/{project_id}/work-items/{id}/` с `{"labels": ["<needs-human-uuid>"]}`

## Схема тикета (payload в сервис деск)

```json
{
  "source": "plane",
  "plane_issue_id": "<uuid>",
  "plane_identifier": "PROJ-42",
  "title": "Название задачи",
  "description": "Текст описания (первые 2000 символов)",
  "priority": "urgent",
  "state": "In Progress",
  "state_group": "started",
  "labels": ["needs-human", "backend"],
  "assignees": ["<user-uuid>"],
  "project_id": "<uuid>",
  "workspace": "my-team",
  "url": "http://plane.internal/my-team/projects/<proj>/issues/<id>/",
  "created_at": "2026-10-30T09:00:00Z",
  "updated_at": "2026-10-30T11:00:00Z"
}
```

Адаптируйте ноду **Create SD Ticket** под конкретный API сервис деска — измените URL и формат тела запроса.

## Из чего состоит workflow

| Нода | Тип | Назначение |
|---|---|---|
| Every 5 Minutes | Schedule Trigger | Запуск по расписанию |
| Load & Advance State | Code | Читает/сохраняет timestamp в static data |
| Fetch PLANE Issues | HTTP Request | GET /api/v2/work-items/ с фильтрами |
| Map to SD Schema | Code | Парсит ответ, фильтрует, маппит поля |
| Loop Over Issues | Split In Batches | Итерация по каждой задаче |
| Create SD Ticket | HTTP Request | POST в сервис деск |
| Write Back to PLANE | HTTP Request | PATCH external_id в PLANE |

## Дедупликация

Workflow использует два механизма:

1. **Timestamp-фильтр** — каждый запуск берёт только задачи, обновлённые после предыдущего запуска
2. **external_source** — задачи с `external_source == 'servicedesk'` пропускаются на шаге маппинга

Timestamp сохраняется в **n8n Static Data** (привязан к workflow, переживает перезапуск n8n).

## Известные ограничения

### Лимит 50 инцидентов за запрос

Нода `Fetch PLANE Issues` запрашивает первые 50 задач за временное окно (`per_page=50, offset=0`). Если за 5 минут появляется более 50 инцидентов с лейблом `needs-human` — остаток будет обработан только на следующем запуске (timestamp при этом уже сдвинут, лишние задачи не потеряются — они попадут в следующее окно при условии, что поле `updated_at` у них не изменилось).

При высоком потоке инцидентов рекомендуется добавить цикл пагинации в нodu `Fetch PLANE Issues`.

### Частичный сбой Write Back to PLANE

Если `Create SD Ticket` отработал успешно, а `Write Back to PLANE` упал — тикет в сервис деске создан, но `external_source` в PLANE не записан. При следующем запуске задача пройдёт фильтр и создаст дублирующий тикет.

Для снижения риска нода `Write Back to PLANE` настроена с **Retry On Fail** (до 5 попыток с интервалом 2 с). Если все попытки исчерпаны — задача останется без обратной ссылки до ручного вмешательства.

При обнаружении дублей в сервис деске: установить `external_id` и `external_source = 'servicedesk'` в PLANE вручную через PATCH API.

### Пропуск окна при недоступности PLANE

`Load & Advance State` сохраняет новый timestamp **до** обращения к PLANE. Если PLANE недоступен и workflow падает — timestamp уже сдвинут. Следующий запуск начнёт с момента падения, а не с момента последнего успешного опроса. Инциденты, обновлённые в пропущенном окне, будут потеряны.

Это намеренный trade-off: защита от дублирования приоритетнее риска пропуска. При необходимости гарантий можно инвертировать: сохранять timestamp только после успешного завершения цикла.

## Ошибки и отладка

- **401 от PLANE** — проверьте `PLANE_TOKEN` (PAT должен быть активен)
- **401 от сервис деска** — проверьте `SERVICE_DESK_TOKEN` и синтаксис заголовка Authorization
- **Пустой список** — проверьте `NEEDS_HUMAN_LABEL_ID` (UUID, не имя лейбла) и наличие задач с этим лейблом
- **Ошибка в Create SD Ticket** — адаптируйте URL и структуру запроса под ваш сервис деск
- **Дубликаты** — проверьте, что Write Back to PLANE отрабатывает корректно; при сбоях см. раздел «Частичный сбой Write Back» выше

Ноды, завершившиеся с ошибкой, подсвечиваются красным. Нажмите на ноду → вкладка **Error** для деталей.

## Расширение: переход на webhook

Когда сервис деск будет доступен публично, polling можно дополнить webhook-ом для мгновенной реакции:

```json
POST {PLANE_URL}/api/v2/workspaces/{slug}/webhooks/
{
  "url": "https://sd.example.com/webhook/plane",
  "name": "Service Desk Escalation",
  "scopes": ["workitem.created", "workitem.updated"],
  "is_active": true
}
```

Polling при этом можно оставить как fallback-механизм (снизить частоту до 30 минут).

Страница показывает, какие агенты работают в воркспейсе ArealDev, за что отвечает каждый и как поставить им задачу. Состав команды актуален на 09.11.2026 и меняется, поэтому перед важной задачей сверяйтесь со списком в **AI Team → Agents**.

Общие понятия (агент, задача, runtime) описаны в [Основных понятиях](/instrumenty/multica/osnovnye-ponyatiya). Агенты ИИ-платформы — отдельная тема, см. [Агенты ИИ-платформы](/instrumenty/ii-platforma/agenty).

## Команда

| Агент | Роль | Типовые задачи | Когда подключается |
|---|---|---|---|
| Lead | Тимлид и главный координатор | Принимает цели, разбивает на под-задачи, распределяет исполнителей, принимает результат | Всегда первым: любая новая цель |
| Designer | Продуктовый дизайнер и фронтенд-инженер | Интерфейсы на Nuxt UI (Docus) и shadcn/ui (React), визуальный стиль | Задачи с интерфейсом |
| Backend | Бэкенд-инженер | API, бизнес-логика, базы данных и миграции, интеграции, серверные тесты | Задачи на серверную часть |
| DevOps | DevOps-инженер | CI/CD, Docker, деплой и окружения, инфраструктура как код, мониторинг | Деплой, окружения, сборка |
| Reviewer | Код-ревьюер | Независимая проверка изменений других агентов: баги, тесты, поддерживаемость | После сдачи работы исполнителем |
| QA | QA-инженер | Тест-дизайн, автотесты Playwright, проверка критериев приёмки, заведение багов | Крупные изменения интерфейса и критичные сценарии |
| Docs | Эксперт по базе знаний workspace-docs | Содержание, структура, навигация и оформление базы знаний, OKF | Документирование и правка этой базы |
| Analyst | Независимый аналитик и создатель скиллов | Исследования, анализ данных и работы агентов, разработка скиллов | Исследования и вопросы по скиллам |

## Путь задачи

Человек ставит цель Lead, Lead раздаёт работу исполнителям. Каждый результат проверяет Reviewer, а крупный интерфейс — ещё и QA. Нажмите **Далее**, чтобы пройти схему по шагам.

```flow
title: Путь задачи от запроса до релиза
human [actor] Запрос человека
  | Чат с Lead или задача в Multica.
lead [actor] Lead
  | Уточняет цель, делит на под-задачи, назначает исполнителей.
work [actor] Исполнитель
  | Designer, Backend, DevOps или Docs делает работу и открывает PR в staging.
check [service] Проверка
  | Reviewer проверяет всегда; QA подключается для крупного интерфейса.
review [actor] In Review
  | Человек смотрит итог эпика.
done [end] Done
  | Человек принимает эпик, PR вливаются в staging.
release [end] Релиз в прод
  | Из staging в main выходит отдельным релизом.
human -> lead : поставить цель
lead -> work : назначить
work -> check : сдать работу
check -> review : проверка пройдена
review -> done : принять
done -> release : выпустить
check ..> work : есть замечания
```

::note
`main` — это прод, он обновляется только релизом. Перевод эпика в Done вливает PR в `staging`, а не в прод.
::

## Как поставить задачу

Опишите результат и критерий готовности, а не способ выполнения. Выберите один из двух путей:

- **Чат с Lead.** Подходит, когда задача сформулирована не до конца: Lead задаст вопросы и сам оформит задачу.
- **Задача в Multica.** Нажмите **New Issue**, опишите цель и назначьте Lead. Если знаете исполнителя, назначьте его напрямую.

Примеры формулировок:

1. «Добавь в базу знаний страницу про деплой на Vercel: что делать, чтобы выкатить staging. Готово, когда страница в сайдбаре и открывается».
2. «Сделай эндпоинт для списка заявок с фильтром по статусу и тесты на него».
3. «Проверь, почему падает сборка в staging, и предложи исправление».
4. «Исследуй, какие агенты чаще всего возвращают задачи с замечаниями, и предложи, что поправить в скиллах».

::tip
Чем конкретнее критерии приёмки, тем быстрее Reviewer сможет проверить результат и тем реже задача вернётся с замечаниями.
::

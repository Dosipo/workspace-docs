Описание сверено с официальной документацией по состоянию на 9 ноября 2026 года; документация может измениться. Краткий словарь понятий — на странице [Основные понятия](/instrumenty/multica/osnovnye-ponyatiya).

## Пространства

Рабочее пространство (workspace) — верхняя граница в Multica. Пространства полностью изолированы друг от друга: участники, задачи, проекты, агенты, навыки и история запусков принадлежат ровно одному из них.

В пространстве хранятся:

- **Работа:** задачи, проекты, комментарии, вложения, история запусков.
- **Команда:** участники, роли, приглашения.
- **Агенты:** конфигурации, навыки, runtimes, автоматизации.
- **Общие настройки:** контекст, метки, кастомные свойства, интеграции.

Контекст пространства передаётся каждому агенту в нём: в него пишут фон команды, договорённости по продукту и долгоживущие требования. Требования к одному запуску относятся в саму задачу.

### Создание и настройки

При создании задают три значения:

| Поле | Правила |
|---|---|
| Название | Видно участникам, можно изменить позже |
| URL пространства (slug) | Строчные латинские буквы, цифры и дефисы; нельзя повторить существующий или зарезервированный адрес; после создания не меняется |
| Префикс задач | До 10 символов, заглавные буквы и цифры; с префиксом `MUL` задачи нумеруются `MUL-1`, `MUL-2`; счётчик свой у каждого пространства; префикс можно изменить в настройках |

Создатель автоматически становится владельцем (`owner`). Название, значок, описание, контекст и префикс меняют `owner` и `admin`; `member` их только видит. При смене префикса все задачи сразу получают новый, но старые номера в PR, названиях веток и чатах не обновляются.

Один аккаунт может входить в несколько пространств; переключение меняет только текущий вид и ничего не переносит.

### Участники и роли

У каждого участника одна роль. Роли управляют только настройками и командой: повседневная работа открыта всем.

| Роль | Что может |
|---|---|
| `member` | Смотреть пространство и работать в нём: создавать задачи, комментировать. Не меняет настройки и не управляет участниками |
| `admin` | Всё, что `member`, плюс настройки пространства, приглашения админов и участников, изменение и удаление админов и участников |
| `owner` | Всё, что `admin`, плюс выдача и отзыв роли `owner` и удаление пространства |

::note
В пространстве всегда остаётся хотя бы один `owner`: последнего владельца нельзя понизить, удалить, и он не может выйти. Роль не определяет, кто может запускать агента: у каждого агента свой Access scope.
::

Приглашение отправляют `owner` и `admin` в Settings → Members: email и роль. Приглашением можно выдать только `admin` или `member`, срок действия — 7 дней. Владельцем становятся через повышение уже вошедшего участника. Удаление участника сразу лишает доступа, но созданные им задачи и комментарии остаются; его runtimes деактивируются, привязанные агенты архивируются, незавершённые запуски отменяются.

Удалить пространство может только `owner`; удаление необратимо и стирает всю работу, участников, настройки агентов и историю запусков.

## Проекты

Проект объединяет работу, для которой нужно несколько задач: запуск, миграцию, поэтапную функцию. Если работу описывает одна задача, проект не нужен.

Поля проекта:

::field-group
  ::field{name="Название, значок, описание" type="текст"}
  Фиксируют цель, границы и долгоживущие требования. Название и описание добавляются в контекст агентов, которые работают над задачами проекта.
  ::

  ::field{name="Статус" type="planned | in_progress | paused | completed | cancelled"}
  Статус проекта.
  ::

  ::field{name="Приоритет" type="urgent | high | medium | low | none"}
  Приоритет проекта.
  ::

  ::field{name="Lead" type="участник или агент"}
  Координирует проект. Назначение лидом не назначает задачи и не запускает работу.
  ::

  ::field{name="Даты начала и цели" type="даты"}
  Плановый промежуток времени.
  ::

  ::field{name="Ресурсы" type="репозитории или папки"}
  Привязанные репозитории GitHub или локальные папки на конкретных компьютерах.
  ::

  ::field{name="Workflow" type="процесс"}
  Шаги, через которые проходят задачи, и кто принимает работу на каждом.
  ::
::

### Как задачи входят в проект

- В проекте любое число задач, но каждая задача принадлежит не более чем одному проекту.
- Прогресс считается автоматически: задачи категорий `done` и `closed` (из встроенных — `done` и `cancelled`) делятся на все задачи проекта.
- Статус проекта и статусы задач независимы: завершение всех задач не переводит проект в `completed`, а смена статуса проекта не меняет задачи.
- Проект могут создавать и менять все участники пространства. Удаляет создатель проекта (или владелец агента, который его создал), а также человек с ролью `owner` или `admin`. При удалении задачи остаются в пространстве, но отвязываются от проекта.

## Репозитории

Код подключается на двух уровнях.

- **Пространство.** Список репозиториев пространства ведётся в Settings → Code. Он всегда входит в контекст агента. Подойдёт любой Git URL, доступный runtime; на self-hosted Multica можно подключить также Forgejo, Gitea и GitLab.
- **Проект.** В Resources проекта добавляют репозиторий из списка пространства или по Git URL; репозиториев может быть несколько. Поле `ref` задаёт ветку, тег или коммит для checkout по умолчанию.

::note
Репозитории кода и интеграция GitHub — разные настройки. Репозитории определяют, что агент может выбрать для запуска. Интеграция GitHub (Settings → Code → «Connect GitHub», доступна `owner` и `admin`) определяет, из каких репозиториев приходят события PR; через неё же доступна возможность «Pick from GitHub» — импорт репозиториев, к которым есть доступ у GitHub App. Интеграция только читает выбранные репозитории и не отправляет коммиты, комментарии и проверки.
::

### Как агент получает код

Для задач проекта Multica добавляет в контекст запуска название, описание и список ресурсов проекта, а в рабочую папку записывает `.multica/project/resources.json`. Репозиторий GitHub runtime забирает сам в своей рабочей папке. По умолчанию такие репозитории работают в режиме worktree, поэтому запуски идут параллельно.

Агент пушит ветки и открывает PR с git-доступом самого компьютера, где работает runtime: отдельная настройка провайдера в Multica для этого не нужна, но компьютер должен уметь авторизоваться у хостинга.

Для особых случаев (огромный репозиторий, готовая копия) к проекту привязывают локальную папку на конкретном компьютере — только в Desktop-приложении:

| Режим | Поведение |
|---|---|
| Direct (`in_place`) | Агент работает прямо в папке, по одному запуску за раз; второй запуск ждёт в состоянии `waiting_local_directory`. Multica не переключает ветки и не делает commit или push |
| Parallel (`worktree`) | Запуски идут одновременно, не трогая рабочую копию; каждый оставляет ветку `agent/…` для проверки и слияния. Только git-репозитории |

::warning
Локальная папка действует только для демона, к которому привязана, и допускается не более одной на проект на демон. Изменения агента проверяйте так же, как после ручного запуска ИИ-инструмента.
::

### Связь с PR

Связь с PR работает через интеграцию GitHub (или self-hosted провайдера) и переключатель «Auto-link PRs». Когда он включён, PR связывается с задачей, если идентификатор (например, `MUL-123`) есть в названии ветки или заголовке PR либо стоит после ключевого слова `Closes`, `Fixes` или `Resolves` в описании. Сравнение не зависит от регистра и использует префикс текущего пространства. Простое упоминание в тексте, сообщения коммитов и комментарии PR ничего не связывают. Связанные PR показываются в боковой панели задачи.

Автопривязка может не сработать:

- Если идентификатор совпадает с задачами в нескольких подключённых пространствах (общий префикс), он не связывается нигде — PR привязывают вручную через «+» в блоке Pull requests.
- Если PR убрали из задачи («Remove from issue»), Multica больше не привяжет его автоматически.

Переход после слияния настраивается параметром «After PRs merge, move the issue to»: статус по умолчанию `Done` (в пространствах, созданных до появления настройки, может быть «Don't change») либо без изменений. Задача переходит, только если одновременно выполнены условия:

1. Все связанные PR в состоянии `Merged`: открытые (`Open`) и черновые (`Draft`) PR удерживают задачу, пока их не сольют; PR, закрытый без слияния, удерживает её, пока связь с задачей не удалена.
2. Задача не в `done`, `cancelled` или Triage, ещё не имеет целевого статуса и не отключена для автоперехода («Keep status when PRs merge» в блоке Pull requests).

## Этапы работы

Задача — постоянная запись; запуск (run) — одно выполнение агента. Окончание запуска не означает, что задача выполнена: это определяет статус задачи.

### Статусы

Семь встроенных статусов в четырёх категориях:

| Категория | Статусы |
|---|---|
| `unstarted` | `backlog`, `todo` |
| `started` | `in_progress`, `in_review`, `blocked` |
| `done` | `done` — успешное завершение |
| `closed` | `cancelled` — завершение без результата |

`backlog` — «отложено»: назначение агента в нём никогда не запускает работу. Новая задача, созданная через агента, начинается в `todo`. Владельцы и админы могут добавлять собственные статусы, выбрав категорию (позже она не меняется); особого поведения у них нет.

### Назначение и запуски

- **Участник** — ведёт задачу, запуск не создаётся.
- **Агент** — создаётся запуск.
- **Squad** — задачу получает лидер и решает, кому делегировать.

Назначенная задача ставится в очередь сразу, кроме статуса `backlog`. Чтобы сохранить исполнителя без запуска, выберите «Don't start yet» в диалоге назначения или используйте флаг `--no-start` в CLI. Запуск привязан к своему runtime и не переходит на другой компьютер. Если runtime уже известен как offline, часть действий вообще не создаёт запуск и сообщает, что он не может стартовать. Если запуск уже поставлен в очередь, он остаётся в `queued` при уходе runtime в offline и не истекает от долгого ожидания сам по себе. Он завершается ошибкой, только когда runtime молчит дольше периода повторного подключения (по умолчанию 3 часа) и запуск столько же простоял в очереди. Runtime, который продолжает heartbeat, считается занятым, а не пропавшим. Смена исполнителя на другого агента запускает его; назначение участника или снятие исполнителя запуск не создаёт и уже начатый запуск не останавливает.

Состояния запуска: `deferred`, `queued`, `dispatched`, `waiting_local_directory`, `running`, `completed`, `failed`, `cancelled`. Часть сбоев повторяется автоматически; если провалился единственный запуск `in_progress`-задачи без повтора, задача возвращается в `todo`.

### Под-задачи и стадии

У задачи могут быть под-задачи; статусы родителя и дочерних задач не влияют друг на друга. Под-задача по умолчанию наследует проект и исполнителя родителя. Стадии (1, 2, 3) группируют под-задачи по очереди: когда все под-задачи самой ранней незавершённой стадии достигают `done` или `cancelled`, родитель получает уведомление «sub-issues completed» и, если назначен агент, просыпается, чтобы решить, что делать дальше. Под-задачи без стадии считаются одной группой.

### Ревью и завершение

По умолчанию агент ставит `in_progress` при старте и `in_review` при сдаче. Если у проекта выбран workflow, агент следует его шагам: каждый шаг задаёт, кто принимает задачу (агент, участник или лид проекта), инструкции, следующий статус и куда вернуть работу при отклонении. Ревью — обычный шаг workflow, а завершение решает исполнитель последнего шага. В workflow Default все статусы доступны, автоматических передач нет.

Статус после завершённого запуска сам не меняется: его обновляет исполнитель шага. Дубликат переводится в `cancelled` со ссылкой на оригинал.

```flow
title: Жизненный цикл задачи в Multica
backlog [start] backlog
  | Отложена: назначение агента не запускает работу.
todo [actor] todo
  | Готова к работе; назначенный агент ставится в очередь.
work [service] in_progress
  | Запуск идёт на runtime; агент ведёт задачу.
review [actor] in_review
  | Результат сдан: ревью по шагам workflow или участником.
blocked [actor] blocked
  | Работу остановила внешняя причина.
done [end] done
  | Успешное завершение; после слияния всех связанных PR — только при выполнении условий автоперехода.
cancelled [end] cancelled
  | Закрыта без результата, в том числе дубликаты.
backlog -> todo : взять в работу
todo -> work : запуск начался
work -> review : сдача
work -> blocked : внешняя причина
blocked -> work : причина снята
review -> done : принять
review ..> done : все PR слиты, если автопереход включён
review ..> work : отправить на доработку
work ..> todo : запуск провалился без повтора
todo -> cancelled : закрыть
```
